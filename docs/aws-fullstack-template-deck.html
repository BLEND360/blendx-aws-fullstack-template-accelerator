The Problem

Every AWS team pays the same first weeks

Before a line of product code, a new AWS app at Blend has to solve private ingress, IAM, container builds, keyless CI/CD and SSO. If there's an agent in it, it also has to stream a harness response to a browser without leaking infrastructure to the client. The Snowflake vertical has a template for this. The AWS vertical doesn't.

Invisible coupling

The MVP is two repos. The backend stack creates the frontend's bucket and CDN, and the frontend can't deploy without it. That dependency is real, but you can't see it from either repo.

Scattered literals

The same values are written in several places: ALLOWED_MODEL_IDS in three files, plus the project name, table names and pool id, each with a comment warning they must stay in sync.

Hand-made pieces

Cognito was created in the console and its ids live in documentation. The first deploy relies on "an engineer runs cdk deploy locally once." Nothing a template can copy.

The opportunity: the MVP already has a working version of almost all of this. The work is to extract it: keep what runs, drop the product domain and the migration workarounds, and put every value in a single file.

The Proposal

Clone, set four values, push

blendx-fullstack-aws-template plays the role for AWS that blendx-fullstack-app-template plays for Snowflake/SPCS. The output is a running app on a private AWS topology with an agent responding.

Deployment Model

One public surface, everything else private

CloudFront is the only public entry point. It serves the SPA from a private bucket through origin access control, and forwards API paths to an internal ALB through a VPC origin. Neither the bucket nor the load balancer is reachable from the internet.

No reverse proxy

The Snowflake template needs an Nginx container to route. On AWS, CloudFront behaviors do that job at no container CPU cost, and you get a CDN with it.

Dev = prod routing

Vite's dev proxy mirrors the CloudFront paths. The SPA never needs an API base URL, so the template has no CORS configuration at all.

One stack per lifetime

Roles, auth, data, harness and app each get their own stack. Rolling back the app can never delete user data.

Core Deliverable

The harness integration layer

This is the part of the MVP most worth extracting, and it's not a thin wrapper: ~1,200 lines across four files. It defines how custom business logic invokes a harness and streams the result to a browser. The browser sends only { "message": "..." }.

the published contract — pinned by tests on both sides (ST-10)
delta · tool_started · tool_input · tool_finished · done · error # mid-stream failure: no HTTP status left to set { "type": "error", "code": "harness_unavailable", "retryable": true, "requestId": "…" }

The hard parts, already solved in the MVP

  • The blocking SDK iterator is bridged to an async generator, with the request id re-bound inside the worker thread
  • A read timeout tells a slow turn apart from a wedged one
  • Protocol sentinels are filtered with lookbehind, because a sentinel can arrive split across two chunks
  • An unknown or failing tool becomes a tool result sent to the model instead of an exception that ends the turn

Security · Replaceability

Three rules at the boundary, one config line to swap the agent

The integration layer is written against a harness it consumes, never against infrastructure it owns. The template ships a minimal starter harness so a clone works on day one, but the app never depends on its shape.

Rules the layer enforces
Rule 1
The backend controls what the agent can do
The browser sends a message, ids and override values. It never sends an ARN, a memory coordinate, an S3 skill URI or an executable tool reference. Only the backend resolves an id to something executable.
Rule 2
Frozen runtime snapshots
A session freezes its validated model, tools and prompt before the first turn. A later template edit can't reach into a running session.
Rule 3
No upstream text reaches the client
A botocore message names the role, account and resource. It's mapped to a fixed sentence, a <dependency>_<category> code and a retryable flag, and the original is logged against the request id.
project.toml — bring your own harness
[harness] arn = "" # empty → deploy the starter harness endpoint = "PROD" # which alias to invoke model_id = "us.anthropic.claude-sonnet-4-5-…"
harness/app/assistant/harness.json — the whole starter harness
{ "name": "my_app", "model": { "provider": "bedrock", "modelId": "…" }, "executionRoleArn": "arn:…", "memory": { "mode": "managed" } }
Aligned with the platform: immutable versions, aliases as environments, deployed with agentcore validate / deploy using the Hub's naming (AgentCore-<name>-<target>). Resolving (ARN, endpoint) instead of a bare ARN means staging, promotion and rollback are all a matter of repointing an endpoint. A template-born harness can move into the Hub later without being rebuilt.

Architecture Standard

A modular monolith, hexagonal inside, delivered as a golden path

Three choices, each answering a different question. The pattern isn't "the most sophisticated one available". It's the cheapest one that still makes the wrong thing awkward to build.

Deploy Modular monolith

One container, in folders that could each become a container. A two-person team ships without running a distributed system, and splitting a service out later is still possible.

Structure Ports & adapters

Business logic never imports AWS. A declared HarnessPort plus a fake that replays a recorded stream means the test suite passes with no AWS credentials.

Adopt Golden path

Template + guardrails + CI gates. import-linter enforces the layers in CI in about fifteen lines of config, so the standard is executable, not prose.

Extraction · Delivery

Extraction, not migration, and one ordered keyless deploy

Nothing is lifted with its history or its workarounds. The MVP's app stack pins every logical id and deletes properties from the rendered template, because it was migrated onto a live stack. A greenfield template has no live stack, so those constructs stay in the MVP, where they're true.

.github/workflows/deploy.yml — one ordered chain
push → test (api, web, infra) → roles # IAM before anything references it → auth # Cognito ids feed task + SPA build → data # tables before the API points at them → harness # skipped if project.toml names an ARN → image # immutable tag <sha>-<run_attempt> → app stack # ECS, ALB, S3, CloudFront → SPA publish + invalidate → smoke test # asserts JSON, not just 200
Lessons the MVP learned the hard way, built in: parallel path-triggered workflows let an image go live before its task role had its grants, so the template uses one ordered chain. A missing CloudFront behavior returns 200 with index.html, so the smoke test checks the body. Declared SG egress was removed twice on rollback, so egress is left undeclared.

Decisions · Next Steps

What we need to start

One decision blocks work, and it isn't needed until Sprint 2. The rest can be settled during implementation.

Blocking
Does the template create a VPC or import one?
A team with no VPC can't deploy today. Proposed: create a minimal VPC by default, with an import-by-id override. Needed before Sprint 2 (ST-07.1, ST-14).
Open
Is SAML federation on by default?
Proposed: native Cognito users by default, and SAML behind a flag driven by a metadata file.
Open
How do clones get fixes?
A GitHub template repo gives no upgrade path. Accept that for v1 and track it for v2.
Resolved
Which harness does a new project use?
Its own starter harness; harness.arn + endpoint override it.
Resolved
Our own CDK stack, or the agentcore CLI for the harness?
The platform's CLI and naming convention, which keeps a template-born harness promotable to the Hub.
Not v1
Register template harnesses in the Hub catalog?
Today that means SQL writes through a bastion, which a clone must not do. Revisit when blendx-aws-foundry-be exposes a write API.
Recommendation
START: SPRINT 25 Approve the scope and the two-sprint plan, and settle the VPC decision before Sprint 26. The work is extraction of code that already runs, so the risk sits in deploy-time behavior, and that's what the buffer and the cut line (ST-12 → ST-13 → ST-11) are for. Core isn't negotiable: without it the template doesn't run end to end, and running end to end is the deliverable.
